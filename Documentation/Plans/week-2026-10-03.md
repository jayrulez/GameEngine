## TAA in the player: a stale bind group (2026-10-03)

User: "why would taa jitter be so bad in the player, but barely noticeable in the editor pie?"
TAA's bind group cache checked only its colour input; the player's first frame gets a different
motion texture than every later one, so one of the two history textures kept frame 0's motion
vectors and every other frame's edges flickered (0.63% of pixels per frame, now 0).
`BindGroupCache` checks every input; MSAA resolve and the SSR and SSGI resolves use it too
(3adbf8c4, 0b60c738, merged eb89f063). The user confirmed the player now matches the editor.
PaperKid's juice and audio merged (39df17e6). Both games then went to FXAA and a fixed exposure
until TAA's resolve and auto exposure are fixed (b4a658bf, 0ab313df; both in the backlog), Sky
Hopper's levels all as bright as its first (67852d42), and the exported players are named for
their game (b1dd4e68).

## The colour pipeline: what is entered is what is seen (2026-10-03)

User: "we need to make the color pipeline consistent so what is entered is what is seen, and
color picker should be srgb", and on the choice: "I don't really care about migration as a
justification. I want the best option." Spec: `Documentation/Specs/color-pipeline.md`.

PaperKid's houses looked pale because the pickers and UI show a colour as sRGB and the renderer
used the same number as linear. The rule now matches images: an authored colour is sRGB and is
decoded once, where it reaches the GPU.

- Core `ToLinear` / `ToSrgb` (412af1d4); extraction decodes every component colour (d8c84631).
- Materials: `Color` and `ColorHdr` property types (emissive is colour plus intensity), decoded
  at the one uniform upload; a stored material adopts its builtin template's colour types as it
  is read; the material page picks its row by type (aa36f9c2).
- Particles decode where they are drawn (c89cd6fb); debug draw decodes in its shaders, with two
  real-device colour probes (ad81b72b); viewport backdrops are sRGB (1ed763b7); the default
  environment colours are written in sRGB (55f58ece).
- Imports: glTF factors are linear by spec and encode on load (40d28176). FBX was assumed to be
  display values; measured on Platformer Game Kit's character (exported as both) it is
  scene-linear too, so it encodes as well (eaaa699c), and its legacy 0.8 diffuse factor is
  ignored to match glTF (user: "ignore the diffuse factor, match glTF", 5b1d2c44).
- Sky Hopper's colours re-expressed in sRGB through the MCP tools, its look kept (d0d33155);
  PaperKid retuned (477336c2; user: "paper kid colors look good").

## A world pose read mid-update is this frame's (2026-10-06)

From the backlog (queued 2026-10-02, PaperKid): `Entity.worldPosition()` inside `onUpdate` read
the world matrix the last `UpdateTransforms` cached, which runs after every script, while
physics interpolation had already written this frame's pose into the local transform: a camera
following it aimed a frame behind (PaperKid's bike shook; the games had worked round it with the
root's local `position()`). `Scene::GetWorldMatrix` now composes the matrix fresh up the local
chain for an entity moved since the last update (its own dirty flag: `MarkDirty` cascades down,
so a moved ancestor marks it), and answers the cache otherwise; the previous matrix (motion
vectors) and the cache are untouched until `UpdateTransforms`. Every mid-update reader (scripts,
IK, animation, the listener) gets the current pose. Sedulous had the same bug and the same pieces
and ports the same shape. Tests: a scene one (a moved parent's child is current at once, the
previous kept, the cache agrees after the update) and a script one (onUpdate moves a parent and
reads the child's world position the same frame). Snowline's scripts had been switched to the
rider's `position()` the same day (9230ba8c).
