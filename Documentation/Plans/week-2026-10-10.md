## Screenshots of the whole editor, over MCP and on F12 (2026-10-10)

From the 0.1 backlog (user 2026-10-10: "We need to be able to take screenshots of the whole
editor over mcp or even from editor hot key"). The whole window could be captured only at launch
(`--screenshot`), and over MCP only a scene viewport or a Game tab.

- `EditorWindowCapture` (Editor.App `:window_capture`): one `ScreenshotCapture` per editor window,
  kept across requests so its readback buffer is made once. A request arms the windows asked for;
  each window's frame records its finished backbuffer after its UI draws; the next update writes
  the PNGs; a window closed before it drew fails its capture. `--screenshot` goes through it too.
- `editor_screenshot` (Editor.App `:mcp_window_tools`, `kWindowToolCount` 1): the main window, or
  with `window: "all"` each open window, the floating ones beside the first file as
  `-window<id>`; it waits for the frames and returns `{path, shots}`, and gives up after ten
  seconds (a minimised editor draws no frame). Default files are
  `<user-data>/screenshots/editor-<pid>-<n>.png`, one counter for every caller. The backlog item
  said to bump `kEngineToolCount`, but that counts the headless engine tools (`Tools.Mcp`); this
  one needs the editor's windows, so it has its own tripwire like the page and action tools.
- View > Screenshot Editor, F12 (an action, so it can be rebound): the main window to a new file
  under `<user-data>/screenshots`, then a toast with its path.

Tests: `Editor.App.Tests` EditorWindowToolsTests over fake window seams (the main window to a
given or new path, "all" with the files beside one another, re-entry until the captures land, a
failed capture, no window, no frame in ten seconds). Run live: `editor_screenshot` on Sky Hopper
returned the 1600 x 900 window, panels and all, and `--screenshot` still writes through the new
capture. Clang and gcc green on Editor.App.Tests (66 cases).

## F frames the selection; entities measured through a scene capability (2026-10-10)

From the 0.1 backlog (user 2026-10-10: "we don't have F key framing for selected entity"), then

  system's answer. The editor asks the scene only, so framing links neither render nor physics,
  and neither of those knows framing exists (the seam foot IK finds the ground through).

  `TransformAABB`) and instanced mesh manager (the set's world sphere extraction keeps); physics's
  rigid body and collider managers (the authored shape: a box, sphere, capsule along y, or a
  cooked shape's outline; a plane is endless and a heightfield is the terrain's). The managers
  answer while editing; physics's scene system exists only while a scene simulates.
- `EditorCamera::FrameSphere`: keeps the view direction, stands back until the sphere fits the
  field of view with a margin, pivots the orbit on its centre (Alt+drag then orbits it); eases
  over `glideSeconds` (0.3 s), `Advance` moving the glide on every frame whether or not the
  viewport has the input, and any camera input stops it where it is.
- `ISceneEditorPage::FrameEntities`: the box holding the entities, each with everything under it
  (a gameplay root's model hangs below it; first built without the subtree, it framed Sky
  Hopper's player at its root's marker, the head filling the view), or the marker's box at an
  entity nothing in which measures.
- Scene > Frame Selection, F (`scene.view.frameSelection`, rebindable, off while the camera
  flies); a double-click on a hierarchy row frames its entity (`OnFrameEntity`; rows no longer
  edit on a double-click); `viewport_frame` (MCP, scene live tools now 19): named entities or the
  selection, at once so a screenshot after shows it, returning the camera.
- The selected entities' boxes in the viewport now come from the same capability instead of a
  list of mesh types, so the box drawn is the one F frames (world-aligned now; a turned mesh's
  box was drawn turned before). Sedulous moves its drawing the same way.

Tests: Scene.Tests (merged answers, none); Engine.Render.Tests (a scaled mesh, an instanced set

## The build scripts made consistent; the editor download can export and be debugged (2026-10-10)

From the 0.1 backlog (user 2026-10-10: the Windows scripts "build with clang but try to package
from msvc build dir. We also don't have any msvc release presets"; and the editor dist "does not
stage the shader files, only the shader pack, so the distributed editor from that script cannot
pack shaders for an export"), then the Windows agent's findings on a crash in the downloaded
editor (an assert, `index < m_size` in `Array::operator[]`, that could not be resolved: the dist
was Release, so asserts were live but no PDB and no debug directory existed), and the user: "for
windows, we always want to build both" shader formats.

- Presets: `msvc-release`, `msvc-reldbg` and `msvc-shipping` beside `msvc` and `msvc-shared`
  (build presets for each, a test preset for `msvc-reldbg`). The `clang*` presets serve Windows as
  they are (clang++ on the MSVC ABI writes `Win64-Clang`).
- Every script configures through a preset, and the folder it copies from follows from the same
  choice: `-Compiler MSVC|Clang` in both `.ps1` scripts picks the preset and so
  `Bin\<Config>\Win64-<Compiler>`; the `.sh` scripts use `clang-release` / `clang-reldbg`, keeping
  the `CXX_COMPILER` override for a versioned clang.
- The editor download is RelWithDebInfo (user's choice over a shipping build): optimised, asserts
  kept, and the symbols split into a `<dist>-symbols` archive kept with the build (the PDBs on
  Windows; on Linux `Tools.Editor.debug`, the exe stripped and linked to it by
  `.gnu_debuglink`). The Windows pack is cooked as DXIL and SPIR-V.
- The download ships the shader sources beside the pack, so an export can cook a game's pack (and,
  later, projects can fork the shaders). The shader host prefers sources whenever DXC has them
  (dev first, so a stray pack never freezes hot reload); the user expected the pack to win when
  present, and on hearing the rule chose a marker: `Shaders/.pack-first`, which the dist scripts
  write, makes `ShaderPackPolicy::Automatic` start from the pack. The dev tree has no marker and
  keeps hot reload.
- CI (user: "Do the CI pipelines need any fixes?"): two did. The symbols archives were built and
  thrown away, so `ci.yml`'s artifacts and `release.yml`'s Release assets now carry the editor's
  and the templates' `-symbols` archives (user's choice: both). And each OS built the engine twice
  (the editor RelWithDebInfo, the templates Release, where the workflows assumed one tree); by the
  user's choice the published desktop templates are RelWithDebInfo too, built from the editor's
  tree. The Linux template's player is staged, its debug info split off and stripped before
  packaging (an export copies the player as it is); the Windows script collects
  `Engine.Player.pdb`. Their ids say RelWithDebInfo (`gameengine-linux64-relwithdebinfo-0.1.0`);
  presets asking for Release find them by the platform fallback, and no sample pins one. Run
  here: the Linux template's player is 19 MB with no debug sections, its 76 MB of debug info beside
  it.
- The editor's periodic resource report (every 15 s, INFO, added for issue I4) is gone (user:
  "That will clean up a lot of log spam"); Project > Report Resource Memory logs one on demand.

Tests: Shaders.System.Tests (a data root with sources, a pack and the marker starts from the pack;
without the marker, from the sources), clang and gcc. Run on Linux: `build-editor-dist.sh` built
the download; unpacked away from the tree, it held the 98 sources, the pack and the marker; the

## A scene grid that fits our scenes, on the plane chosen (2026-10-10)

From the 0.1 backlog (user 2026-10-09; "Also want to handle choosing which plane to draw the grid
on"). The grid was debug-draw lines, a fixed 20 m square of 1 m cells, too small for Snowline's
courses and Lamplight's levels. Of the options discussed (a debug-line grid that follows the
camera; a shader grid on a quad; a full-screen shader pass), the user chose the shader grid on a
quad, and to keep the line grid, off by default, to compare the look and feel.

- `DebugDraw::DrawGridPlane(GridPlaneDesc)` (Foundation.Render): one per list per frame; the
  debug pass draws it first, with its own pipeline and push block (`debug_grid.vs/ps.hlsl`), the
  quad made in the vertex shader from the vertex index, depth-tested like the debug lines so the
  scene hides it, after tonemapping like all debug draw. The fragment shader draws lines at whole
  multiples of the spacing in world coordinates (the quad follows the camera without the lines
  swimming), one pixel wide at any distance by their screen footprint (`fwidth`), every tenth
  heavier, three decades blended so the spacing steps with the camera without a pop, the lines
  through the origin in their axis's colour, fading with distance and where the plane is seen
  edge-on. A pack without the grid shader skips the grid and keeps the lines.
- `:scene_grid` (Editor.Scene): `GridPlane` (XZ, XY, YZ) and its axes; `GridSpacingFor` (a power
  of ten, a tenth of the camera's distance from the plane: 10 m up shows 1 m cells as before, with
  the blend toward the next decade); `GridFadeDistance`. The shader grid, the line grid and the zoom
  readout's "grid cell" all take the spacing from it, so they agree.
- The page: the Overlays menu chooses the plane (Grid on XZ / XY / YZ) and "Grid as lines (to
  compare)"; both are per scene in `SceneViewPref` (appended keys). The line grid uses the same
  spacing, 100 cells each way snapped under the camera, every tenth brighter, with no fade or
  blend.

Tests: Render.Tests (the grid command, the last one wins, cleared each frame);
Render.Backend.Tests DebugGridProbeTests (on a device: a metre grid on XY seen from 5 m lights
the x = 1 line, stays dark half way to it, and draws the Y axis line green); Editor.Scene.Tests
SceneGridTests (the planes' axes, the decade steps and blend, the reach) and the view-state round
trip (plane and style per scene, an older file reading the ground and the shader grid). Clang and
gcc green; the GPU probe suite green. Screenshots to the user: Sky Hopper (metre cells, the
island hiding the grid) and Snowline from 300 m (ten-metre cells over the course).

## The debug-draw leak behind the minimize hang (2026-10-11)

Root-caused on Windows (`prompt-debug-draw-minimize-leak.md`): a long-running editor froze for
seconds on restore from minimized and grew by gigabytes (a 1 to 16 GiB `debug.vtx` buffer). A
minimized window makes `BeginFrame` invalid, so the host skips the render bracket, and
`EndRendering` was the only place the debug lists emptied, while the app kept drawing its grid,
gizmos and wireframes every iteration; the loop, paced only by presenting, spun unthrottled
meanwhile. Two fixes. `RenderSubsystem::EndFrame` (the context's end of every iteration, a frame
rendered or not) empties the debug lists as well, so they hold one iteration at most whatever
the host does; `EndRendering` still empties them, for hosts that render without the loop. And
`ApplicationHost::IdleLastTick` says when an iteration had windows and presented none, so the
desktop runner rests 10 ms instead of spinning a core (the web runner, paced by the browser, is
unchanged).

Tests: Engine.Render.Tests (debug draws across a hundred iterations with no frame rendered never
outlive their iteration, in every list); Runtime.Client.Tests (a minimized window renders
nothing and the tick is idle; restored, it presents again).
