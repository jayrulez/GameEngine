## TAA in the player: a stale bind group (2026-10-03)

User: "why would taa jitter be so bad in the player, but barely noticeable in the editor pie?"
TAA's bind group cache checked only its colour input; the player's first frame gets a different
motion texture than every later one, so one of the two history textures kept frame 0's motion
vectors and every other frame's edges flickered (0.63% of pixels per frame, now 0).
`BindGroupCache` checks every input; MSAA resolve and the SSR and SSGI resolves use it too
(3adbf8c4, 0b60c738, merged eb89f063). The user confirmed the player now matches the editor.
PaperKid's juice and audio merged (39df17e6). Both games then went to FXAA and a fixed exposure
until TAA's resolve and auto exposure are fixed (b4a658bf, 0ab313df; both in the backlog), Sky
Hopper's levels all as bright as its first (67852d42), and the exported players are named for
their game (b1dd4e68).

## The colour pipeline: what is entered is what is seen (2026-10-03)

User: "we need to make the color pipeline consistent so what is entered is what is seen, and
color picker should be srgb", and on the choice: "I don't really care about migration as a
justification. I want the best option." Spec: `Documentation/Specs/color-pipeline.md`.

PaperKid's houses looked pale because the pickers and UI show a colour as sRGB and the renderer
used the same number as linear. The rule now matches images: an authored colour is sRGB and is
decoded once, where it reaches the GPU.

- Core `ToLinear` / `ToSrgb` (412af1d4); extraction decodes every component colour (d8c84631).
- Materials: `Color` and `ColorHdr` property types (emissive is colour plus intensity), decoded
  at the one uniform upload; a stored material adopts its builtin template's colour types as it
  is read; the material page picks its row by type (aa36f9c2).
- Particles decode where they are drawn (c89cd6fb); debug draw decodes in its shaders, with two
  real-device colour probes (ad81b72b); viewport backdrops are sRGB (1ed763b7); the default
  environment colours are written in sRGB (55f58ece).
- Imports: glTF factors are linear by spec and encode on load (40d28176). FBX was assumed to be
  display values; measured on Platformer Game Kit's character (exported as both) it is
  scene-linear too, so it encodes as well (eaaa699c), and its legacy 0.8 diffuse factor is
  ignored to match glTF (user: "ignore the diffuse factor, match glTF", 5b1d2c44).
- Sky Hopper's colours re-expressed in sRGB through the MCP tools, its look kept (d0d33155);
  PaperKid retuned (477336c2; user: "paper kid colors look good").

## A world pose read mid-update is this frame's (2026-10-06)

From the backlog (queued 2026-10-02, PaperKid): `Entity.worldPosition()` inside `onUpdate` read
the world matrix the last `UpdateTransforms` cached, which runs after every script, while
physics interpolation had already written this frame's pose into the local transform: a camera
following it aimed a frame behind (PaperKid's bike shook; the games had worked round it with the
root's local `position()`). `Scene::GetWorldMatrix` now composes the matrix fresh up the local
chain for an entity moved since the last update (its own dirty flag: `MarkDirty` cascades down,
so a moved ancestor marks it), and answers the cache otherwise; the previous matrix (motion
vectors) and the cache are untouched until `UpdateTransforms`. Every mid-update reader (scripts,
IK, animation, the listener) gets the current pose. Sedulous had the same bug and the same pieces
and ports the same shape. Tests: a scene one (a moved parent's child is current at once, the
previous kept, the cache agrees after the update) and a script one (onUpdate moves a parent and
reads the child's world position the same frame). Snowline's scripts had been switched to the
rider's `position()` the same day (9230ba8c).

## SSR reaches, and SSGI stops counting the sky twice (2026-10-06)

Render checks for the fourth demo (Lamplight, a night-time heist), on a test room in a scratch
project (glossy floor, coloured boxes, a metal ball, two point lights) and in new GPU probes
(`Render.Backend.Tests/ScreenSpaceProbeTests`).

SSR (6c2b4cfa): reflections landed in the right place after reverse-Z but stopped short at grazing
angles. Three faults, each hiding the next: the ray's length was the pixel's own depth (a floor seen
from low reflected only a tall object's bottom metre); spread across the screen, a step jumped
further in depth than the fixed hit band and the far reflection broke into a dither; and the band
grown to the step then took the starting pixel itself as a hit, leaving a gap where a reflection meets
what it reflects. Probe: a mirror floor reflects a pillar 8 m tall 20 m away in full (89 red pixels in
its column against 47 for the pillar alone; 47 before). A known limit, not a bug: SSR copies colour
shaded for the camera, so a reflected object's highlights appear mirrored rather than re-lit; a
reflection probe is the answer where it shows.

SSGI: the trace was sound; the composite added the bounce at unit albedo on top of the sky ambient
the forward already applied, so colours washed out and contact shadows vanished. The forward now
writes a diffuse albedo target (a fifth G-buffer target, RGBA8: 22 bytes a sample, under WebGPU's 32;
meshes, terrain, unlit, the MSAA resolve and probe captures follow), and the composite swaps the sky
a hit hides for what the hit found, tinted by that albedo: out = hdr + albedo * (bounce - hitShare *
skyRadiance), skyRadiance being the pixel's own ambient (the scene's SH sky over its normal, scaled
by its dimmer, plus the flat fill). The trace's hit share now weighs each hit by its falloff, and its
firefly average runs over the hits only. A push-constant block written after 56 bytes was read by
HLSL from 64 (Float4 is 4-byte aligned in C++); padded, with a static_assert on the offset. Probes: an
inside corner darkens toward its edge (289 to 235 in luma; additive lifted it), and a blue wall
beside a red one takes no red (8 to 3, the quarter-res gather mixing the walls at the edge; additive
added the red whole). SSGI still needs TAA: without it the few rays show as a fine dither.

## TAA in motion, and a view's history follows the view (2026-10-06)

From the backlog (queued 2026-10-03, "TAA still looks jittery"): PaperKid's levels jittered under TAA
while its title and a test room were steady; the difference was a moving camera. Two faults, each
measured with new GPU probes (`Render.Backend.Tests/TaaProbeTests`) and in PaperKid's player through
a new `--screenshot-count` (consecutive frames from one run):

- TAA dropped history with motion measured as a UV delta times 32: a few pixels a frame cut the
  weight from 0.97 to 0.85, history then spanned fewer frames than the 8-tap jitter, and a chase
  camera showed the raw jitter and the AO noise. Motion is now measured in pixels (history halves at
  32 px a frame). Probe: a camera sliding a pixel a frame strays 2.9 against 1.5 still (7.7 before).
- The state a view carries between frames (previous camera and jitter, TAA, SSR, SSGI and exposure
  histories) was indexed by the view's place in the frame's list. PaperKid's minimap renders on
  alternate frames before the main view, so the main view alternated between places 0 and 1 and
  read the minimap's camera and history every other frame: jitter in the player only (the editor
  adds its views in another order). Views now carry a history key (viewport, or a render texture's
  own view, with the scene and the viewport's corner), and RenderFrame maps keys to stable slots,
  resetting a slot that changes hands. Probe: a view drawn first on alternate frames strays the
  main view 100 by order, 1.5 by key (as alone). PaperKid's player on block 1 now settles to 0 to
  150 changing pixels a frame (2,000 to 3,600 before), as without the minimap.

The probe harness also showed that MeshRenderer keeps each draw's previous world matrix by entity
index, so draws sharing an id take each other's motion. A flash the user then saw in the player
during play is queued in the backlog (not reproduced).

## One draw path for skinned and faded meshes (2026-10-08)

User: "do we not have a non-instanced rendering path?", then "The stated reason looks out of
date... verify this. And if your thought is correct, then could the fade be unified too?" A lone
skinned or faded mesh was forced through the instanced path for a reason that was stale. What
really stood in the way: the vertex shaders left input locations to DXC, which numbers them in
order, so a skinned variant without instance offsets read its joints from the wrong location
(Vulkan drew nothing, WebGPU refused the pipeline); the single path gave this frame's pose as last
frame's; and the fade rode only the instance data. Inputs are pinned with `[[vk::location]]`
(DX12 matches by semantic), the single path carries the previous bone base and a `Fade`, and a run
is instanced only from two draws (4fddd8bf). The TAA probe's batched skinned case did not batch
without a sort key on both copies (0c1eeed5, found by Sedulous).
