the max inverse-distance weight). Keep the normalized-time sync the blend tree
already uses (each clip sampled at `normalizedTime * clip->duration`).

frame step (incl. loop wrap); changing the blend parameter changes WHICH clip's
events fire; no double-fire when both entries carry the same event.

## Seeded: FIX - intermittent AngelScript thread-manager assertion in the cook (user 2026-08-28) - DONE 2026-08-31

FIXED: AngelScriptManager's constructor pins the process-global thread manager
once (asPrepareMultithread, never unprepared - the upstream multi-engine idiom),
so no engine-teardown interleaving can free it early or double-unprepare. Test:
8 sequential engine lifecycles compile a script each; PaperKid cooked 3x clean.


Origin: Tools.Cook aborts intermittently at process teardown with
`asCThreadManager::Unprepare(): Assertion 'threadManager' failed`
(ThirdParty/angelscript/source/as_thread.cpp:193), observed while cooking
several AngelScript scripts (PaperKid: PaperKidGame + Level + Bike) in one
run. NOT harmful in practice - the cooked products are written and the cook
reports success; a plain re-run exits 0. But it is a real crash-on-exit that
would fail CI on a bad roll and is noise during content iteration.

Cause (to confirm): each script cook spins up + tears down its OWN
AngelScript engine, and AngelScript refcounts a PROCESS-GLOBAL thread manager
via asPrepareMultithread / asUnprepareMultithread (first engine creates it,
last release frees it). Cooking N engines in sequence unbalances that
refcount on some interleaving, so a later Unprepare finds `threadManager`
already null and asserts. The multi-engine-per-process cook is the trigger
the single-engine editor/runtime path does not hit.

Fix direction: give the cook ONE owner of the AngelScript thread manager for
its whole run - call asPrepareMultithread once at cook start and
asUnprepareMultithread once at the end (pinning the manager across every
engine create/destroy), or otherwise ensure the AngelScriptManager lifecycle
cannot double-unprepare. Small + contained in the AngelScript cook /
Script.AngelScript backend init.

Tests: cook a project with several AngelScript scripts N times in one process
without the assert (a headless multi-script cook loop); single-script cook
unaffected; products byte-identical.

### AngelScript delegate funcdef surface is ad-hoc (Fable to look into, user 2026-08-19)

Origin: the game-ready-scripting2 P2-6 `button.onClick` seam (script functions as native click handlers via
`IScriptDelegate`; landed 2026-08-19). The native side is general - a reflected `RefPtr<IScriptDelegate>`
param is spelled `?&in`, so ANY funcdef handle is accepted and `Invoke` marshals against the handler's
actual params. The wrinkle is the SCRIPT side: to wrap a function into a delegate handle, AngelScript needs
a PRE-REGISTERED named funcdef, and the backend ships only two ad-hoc shapes (AngelScriptScriptImpl.cpp,
RegisterDelegateSurface):
- `ScriptDelegate` = `double ScriptDelegate(double)` - a confusingly-named, arbitrary double-in/double-out
  shape (it reads as THE delegate type but only fits that one signature).
- `Action` = `void Action()` - the common void no-arg callback (what onClick handlers use).

A handler of any other signature has no funcdef to wrap it, and using the wrong one (`ScriptDelegate` on a
void fn) fails at compile with "Invalid expression: stand-alone anonymous function". Luau has no such limit.
For FABLE: a cleaner delegate-signature scheme - a blessed set of funcdef shapes, an auto-registered funcdef
per reflected delegate-param signature, or at minimum renaming/documenting so `double(double)` is not the
confusing default. NOT urgent - `Action` covers PaperKid's void handlers. (The delegate-callback
`CurrentScriptContext` bug this seam surfaced was already fixed 2026-08-19.) Relates to
[[script-facade-call-syntax]].

### DONE (2026-08-29, user ruling: "make Lua work like AS"): container-PROPERTY semantics
RESOLVED - Luau now binds container members exactly like AngelScript: owner ops
(`<name>_count/_at/_add/_removeAt/_move`, ZERO-based, write-through element handles via the

### (superseded) DECIDE: container-PROPERTY semantics diverge between backends
Luau's PushVariant container branch (LuauScript.cppm ~:1084) converts EVERY container Variant -
property reads and event payloads included, not just facade returns - into a detached 1-indexed
table of element COPIES, so `obj.someArray[1].x = 5` silently writes into a copy. AngelScript
surfaces the same member as mutable `_count()/_at(i)` borrow handles. The two backends now
disagree on container-property mutation semantics. Decide the contract (copy-out everywhere vs
borrow handles everywhere) and add a cross-backend conformance case for a container PROPERTY
read+mutate. Also: move the array-RETURN tests into the shared BackendConformance battery so a
future backend inherits them.

## Landed: GI tier 1 - SSGI (user 2026-09-03)

Second item of the decided renderer order. SsgiPass (:ssgi) is SsrPass's
diffuse twin, structure-identical (trace + temporal resolve, per-view
ping-pong history, generation-keyed bind-group caches with deferred frees):

- **Trace** (ssgi.ps.hlsl): 1-4 stratified cosine-hemisphere rays per pixel
  around the mapped view-space normal, marched against the depth buffer with
  the SSR DDA core (shorter budget: 24 steps/ray, 3.0 view-units radius, 2
  refine iters); hits gather the lit HDR as one-bounce radiance. Noise is
  FRAME-ROTATED (IGN + R2 sequence) - unlike SSR's static dither - so a still
  camera converges under the temporal blend. Misses contribute nothing (the
  ambient/IBL already in the HDR covers off-screen light).
- **Resolve** (ssgi_resolve.ps.hlsl): reproject + YCoCg variance-clip +
  ghost-reject accumulate (blend 0.92 - noisier than SSR, leans on history),
  then composite ADDITIVELY: out = hdr + gi * intensity. RULING (v1):
  unit-albedo approximation - SSR lerp-replaces because it stands in for IBL
  specular; the bounce is added light. Per-pixel albedo modulation arrives
  when the forward integrates indirect terms with the tier-2 probe volume.
- **Placement**: after decals, BEFORE SSR - reflections see the bounce; the
  chain is postHdr -> ssgi.scene -> ssr input. needsMotion ORs in ssgiEnabled
  (the temporal resolve reprojects by velocity).
- **Authoring**: PostProcessSettings.ssgiEnabled/ssgiIntensity (serialized at
  DataVersion 3, reflected with visibleWhen; default OFF - no visual change
  until authored). Editor Post show-flags menu gains "No SSGI"; the master
  disablePost drops it too.
